# CP-PROD-ACCEPT-001 CoordPlane 正式产品化验收合同

## 目标

验证 CoordPlane 已达到可交付产品化状态：多个 CLI Agent 能在隔离运行环境中，通过统一后台服务完成任务领取、通信、证据提交、会话恢复、实时反馈、受控代码协作和最终验
收。验收不检查具体业务项目语义，只检查 CoordPlane 作为多 Agent 协作后台的通用能力是否可靠。

## 验收结论规则

只有同时满足以下条件，才允许声明 product_acceptance.status=passed：

- 全部功能不变量通过。
- 全部正式测试 gate 通过。
- release acceptance 记录写入 durable DB。
- 所有证据来自 CoordPlane public capability/API、coordlink、Docker runtime、数据库投影或红acted inspect 输出。
- 不存在未解释的 environment blocker。
- 不使用旧文件、手工报告、agent 口头声明替代正式证据。

## 必须实现的功能要求

### 1. 常驻后台服务

CoordPlane backend 必须是唯一真相源，负责保存任务、消息、邮箱、租约、会话路由、运行证据、验证结果、代码协作记录和 release acceptance。

要求：

- 使用 file-backed database，不允许以内存状态作为正式验收真相。
- migrations 必须完整纳入 release gate。
- event log、queue、lease、idempotency、retry、failure reason 必须可追溯。
- backend 重启后，未完成任务、mailbox、session route 和 release evidence 仍可恢复读取。

### 2. Capability API

所有 Agent 操作必须通过统一 capability API 进入后台，不允许绕过后台直接写验收文件或调度状态。

必须具备：

- contract.add
- assignment.next
- contract.wait
- contract.complete
- message.send
- communication.read
- mailbox.list
- mailbox.get
- mailbox.resolve
- report.submit
- validation.assessment
- command.run
- 受控代码能力组：workspace prepare/sync/diff/commit/submit/merge/conflict/rollback

每个 capability 必须有明确 input/output/rejected schema。拒绝响应必须告诉 Agent 为什么失败、如何修复、是否可以重试。

### 3. Agent 通信模型

所有 Agent 间通信必须落到统一 AgentCommunicationEnvelope。

必须支持的语义：

- message
- task
- result
- repair
- validation
- budget_attention
- followup

通信不能依赖 Agent 自己记忆，也不能依赖临时 markdown 文件作为真相。

### 4. TeamConfig

TeamConfig 必须定义 Agent、role prompt、skills、runtime、CLI、capability policy 和最终验收策略。

要求：

- 未知 agent、runtime、skill、capability、termination policy 必须 fail-fast。
- capability 不允许硬编码具体角色名。
- 团队角色可以变化，CoordPlane 行为必须仍然成立。
- 最终验收者由 TeamConfig 配置，不由 backend 写死。

### 5. Docker Runtime

正式产品验收必须证明 Docker runtime 可用。

要求：

- 每个 Agent 在独立容器中运行。
- 容器内只看到本地工作区、coordlink 和必要 CLI/toolchain。
- 容器通过专用网络访问 CoordPlane backend。
- 不暴露 backend DB、宿主 runtime 目录、secret、Docker socket。
- 容器启动前完成环境准备，Agent 不需要自行修环境。
- command.run 在 Agent 对应 runtime 中执行，而不是偷偷在 backend 宿主环境执行。

### 6. External Runtime 等价性

external runtime 可用于调试和协议测试，但语义必须与 Docker runtime 一致。

要求：

- 同一 capability 请求在 Docker 和 external 下走同一 backend handler。
- 差异只能是启动方式和执行环境，不能是状态机或权限逻辑。
- external 不能成为绕过 Docker 正式验收的替代路径。

### 7. CLI Agent 会话生命周期

必须支持真实 CLI Agent 的 start、resume、finish。

要求：

- backend 能记录真实 CLI session id、attempt、lease、agent、contract 绑定。
- 子任务完成或新消息到达时，活跃会话优先 same-turn steer；不活跃时 fallback resume。
- resume 后必须回到同一个 Agent 的同一个逻辑会话上下文。
- 容器销毁后，必要的 resume 路由和会话证据仍由 backend 保存。

### 8. 任务完成与验证

Agent 完成任务必须主动调用 capability 提交结果。

要求：

- contract.complete 不能只接受“我完成了”的口头声明。
- 缺少报告、artifact、validation 或 required evidence 时必须 rejected，并给出修复提示。
- validation.assessment 必须写入 canonical validation record。
- root contract 只有在配置的最终验收策略满足后才能 completed。

### 9. 受控代码协作

如果 TeamConfig 启用代码协作能力，Git 操作必须通过 CoordPlane 能力完成并在当前 Agent 会话内返回结果。

要求：

- workspace prepare/sync/diff/commit/submit/merge/rollback 均有 durable evidence。
- 并发提交出现 stale target 时返回明确修复反馈。
- merge conflict 必须能列出冲突、允许 Agent 修复、重新提交并记录证据链。
- 出错后支持 abort/rollback，不留下不可解释的半完成状态。

### 10. 可观测性与证据

正式验收必须输出 redacted evidence。

必须包含：

- release acceptance JSON
- predicate matrix
- redacted inspect
- runtime evidence
- CLI session evidence
- capability call evidence
- validation assessment evidence
- mailbox/resume evidence
- Git changeset evidence
- secret/path leak scan 结果

## 正式测试 Gate

产品化通过必须同时满足：

go test ./... -count=1
go test -race ./... -count=1
scripts/release-health-cp-accept-001.sh
scripts/release-health-cp-probe-001.sh

此外必须有静态/契约 guardrail 覆盖：

- 所有 capability 禁止使用空泛 {"type":"object"} 作为正式 schema。
- store migrations 与 release acceptance required migrations 完全一致。
- AgentCommunicationEnvelope kind 与需求文档一致。
- TeamConfig 引用未知对象时 fail-fast。
- Docker 与 external runtime 共用同一 capability handler。
- release artifact 不泄露 token、宿主路径、Docker socket、CLI 私有配置目录。

## 明确失败条件

出现以下任一情况，验收必须失败：

- 只跑过单元测试但没有真实 Docker/CLI release gate。
- CP-PROBE 只是 environment blocked，却被当作 passed。
- 使用旧 release_acceptance.json 作为当前通过证据。
- backend 状态依赖临时文件或 Agent 工作区文件。
- Agent 可以绕过 capability 直接完成合同或验收。
- Docker 中无法访问 backend，或 command.run 实际跑在宿主机。
- schema 不明确导致 Agent 需要猜参数。
- validation、mailbox、resume、Git conflict 任一关键路径没有 durable evidence。
- secret、auth token、宿主 runtime 路径出现在公开证据中。

## 最终交付判定

当且仅当 CP-PROD-ACCEPT-001 的全部 required predicate 为 passed，并且对应证据已写入 durable DB，CoordPlane 才能声明正式产品化完成。
